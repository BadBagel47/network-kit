# Independent review of network-kit v0.1.0 (2026-11-15)

Made by a separate reviewer agent (strong model, high level) that had not taken part in building v0.1.0. Read-only: nothing in the repository was changed. The findings are tracked in `docs/BACKLOG.md` (IDs in the last column of the table below); the reviewer's proof scripts are in [2026-11-15-proofs/](2026-11-15-proofs/). The proofs marked P and C were run again by the building agent on 2026-11-15 and still demonstrate the faults; the ones against local workerd (`w*.mjs`) were not run again.

Every Cloudflare or GitHub figure marked "unverified" is from memory and needs checking.

## Verdict

- The architecture is sound: a Cloudflare-free core with a fake clock, one alarm for all timers, hibernation-friendly glue, and no per-message storage writes in host-run rooms. All 32 unit and 8 integration tests pass.
- The hard flows have real bugs. The worst are a snapshot rollback and failing duplicate protection after hibernation (both reproduced in real local workerd), server-to-client messages lost on silent reconnects, and a client that gets stuck "offline".
- Nothing limits what one room or one stranger can cost. A single forgotten host tab can eat most of a day's free quota, and an uninvited socket can flood a private room.
- "Host" currently means owner, simulation runner and key holder at once. That, the 0.x version policy, and the auto-push update model should be settled before the first game depends on them.
- Recommendation: one hardening run, released, before the first game goes live on the kit.

## Details (line numbers refer to v0.1.0)

**1. Snapshot rolls back after hibernation**
- Where: `src/server/room-core.js:620-630`, `95-99`, `346-360`, `728-741`
- A snapshot arriving less than `snapshotSaveMs` after the last save stays in memory only. If the room then goes quiet (turn-based game, lobby, game over) it hibernates and that snapshot is gone; a host drop then "saves" and hands over the old one. Same loss when a host leaves with a final snapshot and nobody is online to take over.
- Reproduced in real workerd (`w3.mjs`): snap `{move:1}`, 4 s later `{move:2}`, 25 s idle, host closes → takeover snapshot given to A = `{"move":1}`. With 2 s idle it is `{move:2}`. Also on the fake host (P2, P14).
- Fix: trailing save (a short in-memory timer when a snapshot is kept unsaved) and save on leave/handover.

**2. Duplicate protection fails after hibernation plus a network switch**
- Where: `room-core.js:326-331`, `421-440`
- Relayed messages never persist `lastN`. After hibernation, a new socket for the same player (wifi → 5G, old socket not yet closed) is welcomed with the stale stored `lastN`; the old attachment's `n` is discarded.
- Reproduced in real workerd (`w3.mjs`): 5 messages counted, 25 s idle, replacing socket → `welcome.lastN = 0`. Fake host P1: the host receives `input-1..5` twice.
- Fix: on replace, take `max(player.lastN, old attachment n)` when the session id matches.

**3. A player gone past the grace period replays its recent history on return**
- Where: `room-core.js:412-415`; `src/client/room.js:388-390`, `482-489`
- The client queue is trimmed only at a welcome. A returning player (same page) is created with `lastN: 0`, so up to 500 old messages and commands are resent.
- Reproduced with the real client (C3): the host receives `input-1..5` a second time, and old pause/resume commands flip the room's pause for everyone.
- Fix: keep `{id, sid, lastN}` in `known`; trim the client queue on acknowledgement.

**4. Silent reconnect loses host messages and nobody is told; the takeover "host" message is never repeated**
- Where: `room-core.js:419-438`, `461-473`, `529-531`; `docs/INTEGRATION.md` §4
- When a socket is replaced without the server seeing a drop, no `back` event fires, so the host never resends state. `reliable: true` only covers client → room. If the takeover `host` message lands on a half-open socket, the new host reconnects as host with no `host` event, no snapshot and no `host-ready`, so the room stays paused on `host-change`. Server-run rooms get no `onBack` either.
- Reproduced (C6): A receives only the later message, host peer events `[]`. (C4): `A.isHost = true`, events `[["role",true]]`, paused `"host-change"`.
- Fix: emit `back` (or a new `resync`) on every re-hello of a present player; resend `host` plus snapshot until `host-ready` arrives; correct the docs.

**5. Client stuck "offline" after a brief offline/online blip**
- Where: `room.js:325`, `281-306`, `224-229`, `487`, `502`
- The `offline` event sets status "offline". `online` only probes; the pong does not restore "online". Sends are gated on `status === 'online'`, so they are held back until the socket really dies.
- Reproduced (C1): `status = offline | socket open = true | host got [] | queued = 1`.
- Fix: restore "online" and flush on a pong; gate sends on welcomed plus socket open.

**6. No limit on what one room costs**
- Where: `room-core.js:303-344`, `605-618`; `examples/demo/public/app.js:237-254`
- A host alone in a started game keeps sending positions and snapshots to nobody. One message a second (a throttled background tab) is enough to keep the room awake all day. With the unverified figures in INTEGRATION §7 that is roughly 11,000 of 13,000 GB-s a day; a visible tab at 15 Hz is roughly 66,000 of 100,000 requests.
- There is no per-socket rate cap, no per-room cap and no idle guard. The public demo is an open instance of this.
- By reading plus arithmetic. Check the figures in the account's usage page.
- Fix: the client drops sends that have no online recipient; a per-socket rate cap and a per-room daily cap that close with a final code; auto-pause when one participant is alone for N minutes.

**7. An uninvited socket can flood a private room and block cleanup forever**
- Where: `room-core.js:287-321`, `162-164`, `346-351`
- Before hello, bad JSON or non-object JSON is answered or ignored but the socket is never closed. Hello-less sockets are unlimited. One of them open when the cleanup alarm fires cancels cleanup, and its later close does not re-arm it.
- Reproduced in workerd (`w4.mjs`): private room, no key, 2000 junk messages → not closed, 1000 replies; 50 hello-less sockets stay open. Fake host P7: room still stored 30 days later, `timers: []`, `alarm: null`.
- Fix: close on any pre-hello message that is not a valid hello; cap sockets per room; cleanup counts only identified sockets and is re-armed.

**8. Unvalidated `sid` creates permanent ghost seats**
- Where: `room-core.js:412-418`, `431-434`, `440`
- `sid` can be any size. The player is added to state before `setAttachment`, which throws above 16,384 bytes. The result is an "online" player with no socket and no grace timer. A few hellos fill every seat for good in an open room.
- Reproduced in workerd (`w1b.mjs`): sid of 20,000 chars → no welcome, log `A WebSocket 'attachment' cannot be larger than 16384 bytes`, the host still sees `["ghost","online"]` after the visitor closed. The limit is as observed locally; production is unverified. Smaller sids are stored whole in room state (P8: 400 kB).
- Fix: validate `sid` as a short string; attach before inserting the player; validate `to`, `post` and `id` types.

**9. "Host" is owner, simulation runner and key holder at once**
- Where: `room-core.js:447-451`, `495`, `509-512`, `565-568`, `734-737`
- Each reproduced on the fake host:
  - P11: a 6 s creator glitch in the lobby moves admin rights and the permanent `hostKey` to the next player. The creator does not get them back, and the stand-in pressing Leave closes the room for everyone (`{"code":4000,"reason":"host-left"}`).
  - P12: `hostKey` can never be renewed, so an ex-host passes a private room after ban and key renewal.
  - P13: a server-run room whose host is away past the grace period has `hostId = null` and nobody can start.
- Fix: decide now. Suggested: `ownerId` (creator; admin rights, keys, close) separate from `hostId` (runs the game); never send `hostKey` to a takeover host; the owner reclaims on return. F-013 would otherwise need a breaking change.

**10. The update template's auto-push to a game's `main` is weaker and riskier than it looks**
- Where: `templates/update-network-kit.yml:72-99`; INTEGRATION §1
- A push made with `GITHUB_TOKEN` does not start other workflows (from memory of GitHub's docs; verify with one dry run). The patch lands on `main` but the game's deploy does not run; it ships later with an unrelated push, possibly client and Worker at different times.
- The gate is the game's own tests, which normally do not exercise the kit, so it passes vacuously.
- It runs `scripts/vendor.mjs` from the kit inside the game repo with `contents: write`. Agents push straight to network-kit `main`, so a bad release reaches every game's `main` within 24 h with no human in between.
- No soak time and no way to withdraw a release.
- By reading. The version-finding logic itself is correct (simulated in `find.sh`).
- Fix: ship a kit smoke test for `TEST_COMMAND`; trigger the game's deploy explicitly; take a patch only after N days; default to branch plus issue until trusted.

**11. The version promise does not fit a 0.x kit**
- Where: `CHANGELOG.md` header; `room-core.js:77-81`, `182`; `.github/workflows/release.yml`
- "MINOR: code keeps working" is promised at 0.1.0, yet findings 3, 4, 9 and 13 need behaviour changes. `state.v` is written but never checked on load, and rooms live 24 h across deploys. There is no test of the previous release's client against the new server, and no CI check that a `src/` change comes with a version bump and changelog entry.
- Fix: declare that 0.x MINOR may break (with a guide) and only PATCH is automatic; add a cross-version test and a `v` check.

**12. Viewers and waiting players can pause, and viewer messages reach the host**
- Where: `room-core.js:664-676`, `605-618`
- Reproduced (P6): a viewer-key socket pauses a private game; a `lateJoin: 'next'` waiting player pauses; a viewer's `{fire:true}` is relayed to the host.
- Fix: pause and resume need an admitted player; drop viewer game messages by default.

**13. Queued messages cross the host/player boundary after a role change**
- Where: `room.js:381-390`
- Reproduced (C7): an old host returning after takeover resends its queued host broadcasts, and the new host receives them as player input from the old host. The reverse holds for a player who becomes host.
- Fix: purge or tag the queue on role change.

**14. `join()` never settles when the server is unreachable, and retries forever**
- Where: `room.js:145-149`, `239-253`, `269-278`
- Any failed upgrade (server down, 403 origin, quota exhausted, 500) is retried for ever with a 15 s cap, about 5,760 requests a day per forgotten tab. `NetworkRoom.join` returns no handle to cancel.
- Reproduced (C2): `settled = false`, 37 attempts in 1.5 s with small delays.
- Fix: reject the first connect after a timeout; back off to minutes; stop after a long hidden period.

**15. The `gate` hook cannot deliver F-003/F-004 as written**
- Where: `src/server/worker.js:138-139`; backlog F-003, F-004
- The gate runs on every WebSocket upgrade, including reconnects of admitted players, so "running games finish" breaks at the first glitch after Off (final 4008). Running rooms cannot be reached for an emergency stop, and in-room messages never pass the gate, so a closed game's rooms keep spending.
- By reading.
- Fix: check new joins inside the room; give rooms a cheap stop flag checked on hello and alarm. Mark `gate` experimental now.

**16. A silently dead host freezes the game (F-010) and the proposed mechanism is too slow**
- Where: backlog F-010; `room-core.js:346-360`
- Takeover only starts when the server sees the close. A sleeping phone or closed lid is half-open for an unknown time. A 20 s heartbeat (throttled further in background tabs) cannot give "within seconds".
- By reading.
- Fix: players complain after N s without host data; the room pings the host and takes over if nothing comes back in about 3 s. Do it with the first game's first playtest.

**17. Server-run rooms write storage on every message**
- Where: `room-core.js:796-802`, `627`, `79`
- Reproduced. P17: 100 ignored viewer messages → 100 puts. P15: 20 snapshots in 2 s while paused → 20 puts. P19: one host drop and return → 3 puts and 2 alarm sets. The snapshot is also read on every wake.
- Fix: write only after `room.save()` or the `game` setter; throttle saves while paused; load the snapshot lazily.

**18. Pause can deadlock**
- Where: `room-core.js:149-155`, `664-679`
- Reproduced (P10): `pauseBy: 'nobody'` with `autoPauseMs` → the pause can never be lifted (`resume` → `not-allowed`). A `player-away` pause is not lifted when the player returns or is gone.
- Fix: lift automatic pauses when their cause ends; reject the option combination.

**19. Admitted players are locked out after the grace period**
- Where: `room-core.js:385-418`
- Reproduced (P18): `lateJoin: 'never'`, 61 s away → 4006, final. The same applies to a private room after a key renewal. `known` is only used to reuse the id, and it grows without bound (P8: 202 entries after 200 short visits).
- Fix: let known, not-kicked players return; cap `known`.

**20. Ban is trivially bypassed**
- Where: `room-core.js:375`, `701`
- Reproduced (P12): same invitation link with a new tab (new per-tab key) → back in.
- Fix: document it; have ban renew the keys and switch the room to private.

**21. `room.seed` is public and the reference example derives hidden cards from it**
- Where: `room-core.js:555`; `examples/demo/memory-rules.js:42-52`
- Reproduced (S1): player B computes `[0,3,3,1,2,0,2,1]`, identical to the server's cards.
- Fix: do not publish the seed in server mode, or give rules private randomness. Fix the example.

**22. API details that are cheap to change only now**
- Where: `room-core.js:23`, `589-601`; `room.js:403-415`; `app.js:232-235`
- `posts` is described as "posts on a shared ship", which breaks the project's own rule against naming one game; one holder per post is also baked into `room.posts`.
- `room.phase` stays "countdown" on clients because nothing is broadcast at `startsAt`; every game must reimplement the demo's `running()`.
- `room.isHost` is false inside the `host` handler (C5 reproduced).
- `to: 'all'` and `'players'` echo to the sender; `'host'` is undocumented.
- Rules are synchronous and get no `env`.
- Storage keys are not namespaced per game, and games on `github.io` share an origin.
- Fix: rename and decide before adoption; the rest can be MINOR.

**23. Prototype keys accepted as player ids**
- Where: `room-core.js:655`, `699`, `722`, `119-125`
- Reproduced (P9): host `kick` with id `"__proto__"` → `ok`, and every grace timer is cleared.
- Fix: own-property lookup; no wildcard on an undefined timer key.

**24. Snapshot save not awaited; oversized-message errors are anonymous**
- Where: `room-core.js:308`, `338-339`
- `storeSnapshot` returns a promise that `message()` drops. The `too-large` error for anything over 512 kB carries no `n` or type, and the client has no size check.
- By reading; `w2.mjs` confirms the anonymous error.

**25. Important behaviour is untested**
- The client has no unit tests, and findings 3, 5, 13 and 14 live there. There is no real-hibernation test, although local workerd does hibernate (`w3.mjs`). The browser test is not in CI or the release, though the README says the demo must pass. Untested: gate on join, cleanup with sockets present, server-run host loss, silent socket replacement, the release workflow and the update template.

**26. Docs disagree with the code**
- `AGENTS.md` says "Boomers first"; `docs/HANDOFF.md` says Critical first. `AGENTS.md` also lists opening hours and administration as existing.
- The `room-core.js:2` header names `durable-object.js`.
- INTEGRATION §3 omits the `welcome` and `ok` events, `why` on `peer`, and the client options (`identity`, `autoHostReady`, `maxQueue`, heartbeat).
- INTEGRATION §2 omits `closedKeepMs` and `nameMaxLength`.
- INTEGRATION §8 omits the stored plain `hostKey`, ban hashes, and key hashes of players who already left.

**27. Smaller workflow pitfalls**
- Where: `.github/workflows/release.yml:12`, `51-65`; `templates/update-network-kit.yml:28-32`, `86-99`
- `workflow_dispatch` can tag a non-main commit.
- Nothing checks that the version increases or that the changelog section exists.
- `$SETUP_COMMAND` and `$TEST_COMMAND` are word-split, so `a && b` fails.
- The template assumes the default branch is `main`.
- Scheduled workflows stop after long repo inactivity (unverified).
- The update silently overwrites local edits and does not update the game's recorded version.

## Looks solid

- Alarm and timer bookkeeping: every mutation path ends in `flush()`, and early fire, delete and reload stay consistent.
- Socket replacement and the `closed` flags on attachments; `denied` JSON sent before the close code.
- Keys: 128-bit, constant-time compare, per role, a viewer key can never play, renew and expiry work, only the current host sees them. A refused hello writes nothing.
- The origin check also covers the WebSocket upgrade; gate and bad codes answer without waking a room.
- Hibernation friendliness: no timers in the object, ping/pong auto-response, zero storage writes for relayed messages in host-run rooms (P16).
- The server stamps `from`; only the current host can broadcast, snapshot or run host commands.
- Duplicate protection on the same socket across hibernation.
- Unknown message types and commands are handled gracefully in both directions.
- Each game has its own copy and its own Worker, so kit changes cannot reach a game at run time.
- Release tagging and the template's version selection.

## Plan recommendations (the reviewer's)

- Add a hardening run before the first game goes live: findings 1–8 and 12–14, the decisions in 9, 11 and 22, client unit tests and a real-hibernation test. Release it; breaking changes cost nothing today.
- Do a paper pass of D-012 first: a short check of Buzzy's, Boomers' and Bricks' needs against roles, owner/host, posts or teams, late join and server-run limits. Its value is finding API changes while they are free.
- Pull F-010 forward to the first game's first playtest, with the mechanism in finding 16. Add the missing task "demo on two real phones" (lock screen, wifi → 5G).
- Reorder the administration run: D-011 → F-008 → F-004 → F-003. Each game is its own Worker, so Cloudflare's per-script usage numbers give per-game usage without extra writes (unverified; needs the read-only token). Enforcement is a flag the gate reads with a cache.
- Redesign the gate first (finding 15), and put the per-room caps of finding 6 into the hardening run. They are the real guard against a runaway game; the free plan's hard stop is the backstop.
- F-013: settle owner versus host now. The no-seat host, `takeover: off` and game-defined roles can then be a compatible MINOR.
- Missing items: an abuse and rate-limit item; a kit smoke test that games run in the update workflow; what a player sees when the quota is exhausted; a budget or gate for the public demo; logging in production (`observability` is off in `wrangler.jsonc`).
- A game should not turn on the auto-update workflow until finding 10 is resolved.
- Client integration work in the first game can start in parallel, but it should not ship on v0.1.0.
