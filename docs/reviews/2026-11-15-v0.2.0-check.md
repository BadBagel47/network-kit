# Independent check of the v0.2.0 release candidate (2026-11-15)

Made by a separate reviewer agent before v0.2.0 was released, on the state of the rewrite at that point. Read-only. It re-tested the 27 findings of the [review of v0.1.0](2026-11-15-v0.1.0.md) with its own scripts (including a fuzz of 400 runs of 120 random steps against the default options) and looked for new faults. Everything it found was then fixed or recorded before the release; **those fixes were tested by the building agent, not checked again by an independent reviewer.**

## Verdict of the check

- The shape (owner and host, roles, places, waiting by default) is sound to build on. With default options the reviewer could not get the host role, ownership or the kept snapshot to anyone but the owner.
- The candidate was not yet fit to go live: two faults would have shown in a first playtest (B1, B2), and about ten medium ones were found.
- Of the 27 earlier findings: 16 fixed, 10 partly, 1 not fixed (the gate, which belongs to F-003).

## Findings and what was done

| # | Severity | Finding | Done before the release |
| --- | --- | --- | --- |
| B1 | High | The resend after a reconnect tripped the rate limit; the client was closed for good | The client paces everything it sends under the room's limit and resends in order; tests in Node and in local workerd |
| B2 | High | The owner's second tab (same browser, same stored owner key) took the room from the first | The owner key only claims the owner's seat when that seat is not connected; a second window joins as an ordinary participant |
| B3 | Medium | Duplicates after a host check that follows a sleep | The unanswering host is closed through the normal path, which keeps its message counter |
| B4 | Medium | A next host whose phone is asleep was never detected | Every new or returning host is asked to answer within `hostCheckMs`; if not, the next one is tried |
| B5 | Medium | Server-run rules were not told when the owner moved to another device | The owner keeps the same participant id on another device; rules get `onBack` |
| B6 | Medium | A renewed link or a ban did not shut out those the room remembers | Renewing a link and banning end the standing of absent participants; they can be removed or banned by id while away; leaving on purpose ends it too; no bypass of "late join: never" into a later round |
| B7 | Medium | A viewer could use up the room's budget and cause storage writes | Ignored and refused messages cost the sender (and close it), not the room; commands that change nothing cause no write or broadcast; the host check is kept in memory |
| B8 | Medium | Awake time was not bounded | A cap on busy minutes per room and day (`maxActiveMinutesPerDay`). A backstop only: see F-032 |
| B9 | Medium | The remembered role beat the invitation key and the role asked for | A valid key decides, then an allowed role that is asked for, then the role held before |
| B10 | Medium | A game could be "running" with no connected host | One check, made on every change, pauses the room whenever nobody runs the game |
| B11 | Medium | The guide disagreed with the code in several places | Guide corrected; inputs are sent again when the host is back (guide and demo); without takeover the kept state no longer passes on when ownership passes by itself |
| B12 | Medium | Update template: proposed the same version daily after "skip", starved by frequent patches, silent on an empty VERSION | Rewritten: a version with an issue is not proposed again, the newest patch that is old enough is taken, an empty VERSION or tag list fails |
| B13 | Medium | An older line could get no more fixes once a newer MINOR existed, and games were never told about the newer one | The release check compares within the MAJOR.MINOR line; the template announces a new feature version once |
| B14 | Medium | The smoke test failed for games whose roles all need a link, and passed with broken entry files | It picks a role with a free seat, loads the files a game imports, builds the server from the options, and has takeover and timer steps |
| B15 | Low/Medium | A new owner who missed the rotated owner key could lose the room | The key is sent again whenever the owner connects without it |
| B16 | Low | A room emptied by a host check was never deleted | Fixed with B3; and a room nobody is connected to is always given a cleanup timer |
| B17 | Low | Handover while reconnecting passed on an old state; leaving while disconnected told the room nothing | The newest snapshot is sent first after a reconnect; leaving keeps trying for ten seconds |
| B18 | Low | `vendor.mjs` deleted whatever folder it was given | It refuses a folder that is not empty and is not an earlier copy |
| B19 | Low | Needless host reports right after start; the daily count could be dodged by short bursts | The silence clock starts when play starts and waiting participants do not report; the count is stored before a room that goes quiet sleeps |
| B20 | Low | With the default identity per tab, a link opened again is a new participant | Documented with the alternative (`identity: 'device'`); the default stays |

Also done: the update template's two jobs (the kit's code and the game's tests run with a read-only token; another job pushes the branch and opens the issue).

Left open, recorded in the backlog: the gate (F-003); real detection of a room nobody is playing in, tests of the update template and release workflow in CI, a CI check that a change to `src/` comes with a version bump (F-032).

## Checked and found right by the reviewer

- Default options: no non-owner received the host message, became host or became owner; handover, host-ready, snapshots and owner commands are refused or ignored from others.
- The owner key is compared in constant time, rotated when ownership is given, and only the owner sees the invitation keys.
- Timers and the single alarm; closed rooms forgotten after an hour; snapshots loaded lazily and written at most once per `snapshotSaveMs`.
- Hello for new, known, owner-key, replaced-connection and reloaded-page cases; nobody who slips in before the creator gets the game.
- Places with capacity, seats per role, a viewer key can never play, odd ids, late join.
- Relayed messages cause no storage writes; another version's stored room is discarded.
- The client: offline blip, join timeout, slow-down and give-up, role-change purge, countdown, too-large checks.
- The release workflow; the template never pushes to the default branch.
